**贯穿作品 · 小北的网站**

走到这一章，小北的网站已经像模像样了：React 重构完成，Tailwind 换上了新装，待办清单能存能删，天气小应用也能跑。可是他心里清楚，有不少代码是"照着书敲能跑、合上书就说不清"——让他讲讲某行为什么这么写，他就开始挠头。还有些地方自己看着总觉得别扭，又说不上来哪儿别扭。

这一章，我们给小北请一位随叫随到的陪练：DeepSeek。它是一个国产大模型，在浏览器里打开它的官网、或者在手机上装它的 App，就能直接对话，不用安装任何编程工具。它在本书里的定位不是"写手"，而是"陪练"：陪小北把代码读懂、把报错看懂，最后把主页里藏着的小毛病一个一个挑出来。

学完这一章，小北的主页会被挑出 3 个问题，再被他亲手逐个改好。而你，会多一个随时在线的学习搭子。先把丑话说在前面：**陪练是陪你练的，不是替你上场的。** 这一章从头到尾，都在讲怎么用好它、又不被它带偏。

## 16.1 AI 陪练能做什么、不能做什么

先认识一下这位陪练。"大模型"你可以先简单理解成：一个读过海量文字和代码的程序，你给它一段话，它能根据上下文接出像模像样的下文。DeepSeek 就是这样的国产大模型，对话之外它也开放 API——那是留给程序去调用的接口，本书里我们不用，你只管打开网页或 App 跟它聊天就行。

把它当陪练，它有四样本事特别对口：

- **解释概念**：书上一个概念没看懂，换它用大白话再讲一遍，还能让它"举一个生活中的例子"。
- **读代码**：把一段代码贴给它，让它逐行讲在干什么——这是本章 16.3 的重头戏。
- **查报错**：把控制台的红色报错整段贴过去，让它帮你定位是哪一行、为什么。
- **生成练习**：学完一个知识点，让它按你的水平出几道题，做完再让它批改。

除此之外，它还能帮你出主意："我这个页面还能怎么改进？"它能一口气列出好几条，你再从里面挑。

但有三件事，它做不了，你也别指望：

- **不能替你思考**。做一个什么样的网站、哪个功能先做哪个砍掉，这是你的决定。它给的永远是"参考答案"，不是"标准答案"。
- **不能保证正确**。它写错东西的时候，语气和写对时一模一样自信。这一点 16.4 会专门讲怎么防。
- **不能替你背锅**。交给老师的作业、发到线上的网站，署名都是你。出了问题，"是 AI 让我这么写的"不是理由。

还有一个先天限制要记住：**它没见过你的项目**。你电脑上那些文件长什么样、变量叫什么名字，你不贴给它，它只能靠猜。这一点，正是本章翻车现场的源头。

## 16.2 怎么提问才有效：把问题说清楚的四要素

![提问四要素：背景、目标、已尝试、报错原文，凑齐了 AI 才答得准](../images/fig-ch16-ask.svg)

同样一个陪练，会问的人三言两语拿到答案，不会问的人聊十轮还在原地打转。差距不在运气，在提问方式。一个有效的问题，包含四个要素：

1. **背景**：你是谁、在做什么、用什么写的。比如"我是编程新手，正在做一个 React 加 Tailwind 的个人主页"。
2. **目标**：你想达成什么效果。不是"我想改一下"，而是"点删除按钮后，这一条要从列表里消失"。
3. **已尝试**：你自己先试过什么、试出了什么结果。这一步最容易被跳过，却最重要——它既帮 AI 排除一半可能性，也证明你动过脑子，而不是伸手要答案。
4. **报错原文**：控制台有红字，就整段复制粘贴。不要截图（字小看不清），不要自己翻译转述（一转述，关键的那一行往往就被你漏掉了）。

来看一对真实感很强的对照。坏提问长这样：

> 我的待办清单点删除没反应，怎么回事？

没有背景、没有目标细节、没说自己试过什么。陪练只能反问你一串问题，一来一回全是浪费。再看好提问：

> 我在做一个 React 待办清单（背景）。点每条待办右边的"删除"按钮，我想让这一条从列表里消失（目标）。我给按钮绑了 `onClick`，在函数里用 `filter` 生成新数组、再调用 `setTodos` 更新，但点了之后列表一点变化都没有（已尝试）。控制台没有红色报错（报错情况）。相关代码是这一段：……（贴上代码）

四个要素齐了，还附上了相关代码，陪练基本一轮就能指出问题——比如"你 `filter` 的条件写反了，留下的恰好是要删的那一条"。**把问题说清楚，本身就是一种编程能力**：你能把问题描述到这个程度，其实已经解决一半了。

## 16.3 用 AI 读代码、查报错、补概念

下面是三个最常用的场景，都来自小北这段时间的真实用法，你可以直接照着模仿。

**场景一：贴代码，让它逐行讲。** 小北的待办清单里有这么一行，他能写出来，但说不清细节：

```javascript
const left = todos.filter(item => !item.done).length;
```

他这样问：

> **小北**：请逐句讲这一行代码在干什么，特别是 `filter` 里面那个函数为什么没有写 `return`？
>
> **DeepSeek**：这行做了两步。第一步，`todos.filter(...)` 把数组筛一遍，只留下满足条件的元素；条件是 `item => !item.done`，`!` 是"取反"，意思是"还没勾完的"。箭头函数只有一句表达式时，可以省掉大括号和 `return`，表达式的结果就是返回值。第二步，`.length` 数一下筛完还剩几个，存进 `left`——也就是"还剩几件事没做"。

听完讲解别急着点头，合上答案自己复述一遍，复述不出来的地方，就是你真正没懂的地方，追问它。

**场景二：贴报错，让它定位。** 小北在练原生 JavaScript 时遇到过这段红字：

```bash
Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')
```

他把报错原文连同"我把 script 标签写在了 head 里"一起贴过去，陪练的定位是：`null` 意思是"什么都没找到"——脚本运行时页面上的按钮还没被浏览器加载出来，`querySelector` 自然扑了个空；解决办法是把 `script` 放到 `body` 的最后，或者给它加上 `defer`。顺带记一个看报错的窍门：**先看第一行的错误类型**，`TypeError` 多半是"对一个空值或错类型动了手脚"，`ReferenceError` 多半是"名字不存在"，心里先有谱，再看细节。

**场景三：让它出练习，补概念。** 学完一个知识点，最好的巩固是做题。可以这样交代：

> **小北**：我刚学完数组的 `filter`，请给我出 3 道由易到难的练习题，只给题目和一句提示，先不要给答案。等我写完贴给你，你再帮我检查。

注意那句"先不要给答案"——不加这句，它往往把答案一起端上来，你的练习就白做了。做完贴回去让它批改，错在哪、为什么错，让它讲清楚。

## 16.4 AI 的答案为什么要验证

这一节要泼一点冷水：**AI 说得自信，不等于它说得对。** 前面讲过，它是根据上下文"接下文"的程序，语气只和文字的流畅程度有关，和对错无关。它写错的时候，排版工整、措辞笃定，和写对时没有任何区别。

它常见的错法有这么几种：编一个根本不存在的方法名，听起来特别像真的；把参数顺序记反；给出好几年前的过时写法；还有最隐蔽的一种——代码本身没错，但和你的项目对不上，比如变量名、文件路径用的是它自己编的。最后这种，翻车现场里小北就亲身经历了一次。

好在验证并不难，记住三招：

1. **跑一遍**。把它的代码放进你自己的项目，实际运行，眼见为实。跑不通，就把新的报错原文再贴回去——报错是最诚实的反馈。
2. **查文档**。拿不准的属性、方法，去 MDN 这类官方文档里搜一下对一下。文档是"标准答案"，陪练的说法和文档冲突时，听文档的。
3. **换种问法**。同一个问题换个说法再问一次，或者追问它"为什么要这样写"。两次答案能对上、理由讲得通，可信度才高；一追问就改口的答案，基本可以判定它在瞎编。

**AI 给的是草稿，运行结果才是定稿。** 养成"先验证、再采用"的习惯，你就从"被 AI 牵着走"变成了"指挥 AI 干活"。

## 16.5 贯穿作品：请 DeepSeek 帮小北的主页挑毛病

最后来一次完整的实战。小北把主页几个组件的代码贴给 DeepSeek，按四要素组织了提问：

> 我是编程新手，这是我个人主页的 React 代码（背景）。请帮我检查有没有无障碍和使用体验方面的问题（目标），只挑最重要的 3 个，并告诉我每一个怎么改。我自己看过一遍，觉得排版没什么问题（已尝试）。

陪练挑出了 3 个问题，都不在"排版"上，而在"没想到"上。

**问题一：照片墙的图片没写 `alt`。** `alt` 是图片的"替身文字"：图片加载失败时，浏览器会把这段文字显示在图的位置；视障用户用读屏软件浏览时，念出来的也是它。没写 `alt`，照片墙在这些场景下就是一片空白。改法是给每张图补一句真实描述：

```jsx
{/* 改之前 */}
<img src="/photos/lake.jpg" className="rounded-xl" />

{/* 改之后 */}
<img src="/photos/lake.jpg" alt="傍晚的湖边，天空是橙红色的晚霞" className="rounded-xl" />
```

**问题二：联系表单只有占位提示，没有 `label`。** 小北的表单每个输入框里只有一行灰色的 `placeholder`（占位提示文字）——它有两个毛病：一开始输入，占位文字就消失了，你回头就忘了这一格填什么；而且点那行说明文字，输入框不会获得焦点。在 JSX 里补上 `label`，注意一个小坑：HTML 里的 `for` 属性，在 JSX 里要写成 `htmlFor`：

```jsx
{/* 改之前 */}
<input type="email" placeholder="你的邮箱" className="border rounded px-3 py-2" />

{/* 改之后 */}
<label htmlFor="email" className="block mb-1">你的邮箱</label>
<input id="email" type="email" placeholder="name@example.com" className="border rounded px-3 py-2" />
```

`label` 的 `htmlFor` 和输入框的 `id` 对上号，点击标签就能聚焦到输入框，读屏软件也知道这一格是干什么的。

**问题三：手机端导航挤成一团。** 小北的导航栏是第 15 章写的一行横排，在电脑上没问题，可手机屏幕一窄，"首页、照片、笔记、待办、联系我"全挤在一起，字都叠了。改法用的是第 15 章学过的响应式前缀：小屏纵向排列，大一点再横过来——

```jsx
{/* 改之前 */}
<nav className="flex gap-6">

{/* 改之后 */}
<nav className="flex flex-col items-center gap-2 sm:flex-row sm:gap-6">
```

`flex-col` 让导航在手机上竖着排，`sm:` 前缀表示"屏幕达到小屏断点以上时"再切换成 `flex-row` 横排。三处改完，小北拿手机打开主页挨个验证了一遍：图挂掉时有文字、点标签能聚焦、导航在手机上舒舒服服竖成一列。

这 3 个问题有个共同点：**都不是代码写错了，而是写代码时没想到。** 基本功决定你能不能把网站做出来，而这样一位陪练，能帮你把"没想到"的地方一点点补上。

## 本章要点

- DeepSeek 是国产大模型，打开网页或 App 就能对话，本书把它当作 AI 陪练：问概念、读代码、查报错、生成练习。
- 陪练能解释、能定位、能出题，但不能替你思考、不能保证正确、不能替你背锅。
- 提问四要素：背景、目标、已尝试、报错原文；报错要整段复制，不截图、不转述。
- 让 AI 讲代码、查报错时，听完要自己复述、实际运行，讲不清跑不通就是没懂。
- AI 的语气和对错无关：它可能编不存在的方法、给过时写法、和你的项目对不上。
- 验证三招：跑一遍、查文档、换种问法；AI 给的是草稿，运行结果才是定稿。
- 挑毛病三连：图片补 `alt`、表单补 `label`、导航做响应式——都是"没想到"而非"写错"。

## 动手 Kata

1. **逐行讲代码**：打开 DeepSeek 网页版或 App，把你第 10 章待办清单里任意一段 JavaScript 代码贴进去，让它逐行讲。听完合上答案，自己对着代码复述一遍。做完效果：每一段代码你都能说清在干什么，卡住的那一行就是下一个要追问的问题。
2. **把坏提问改成好提问**：翻出你最近遇到的一次报错，先按平时的习惯写下你会怎么问；再按四要素（背景、目标、已尝试、报错原文）重写一遍，两个版本都发给 DeepSeek，对比回答。做完效果：你能明显感到好提问的回答更准、更短、更能直接动手。
3. **让它出题并批改**：挑一个刚学完的知识点（比如 `map` 或 Flex 布局），让 DeepSeek 出 3 道由易到难的题，并明确要求"先不要给答案"。自己做完后贴回去让它批改。做完效果：错题的原因被讲清楚，而不是只知道对错。
4. **给自己的主页挑毛病**：把你主页任意一个页面的代码贴给 DeepSeek，请它挑 3 个无障碍或体验方面的问题，并逐个动手改掉、运行验证。做完效果：主页至少修好一处真实问题，你也走完了一遍"提问—修改—验证"的完整流程。
