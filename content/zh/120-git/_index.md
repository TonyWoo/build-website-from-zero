**贯穿作品 · 小北的网站**

昨天晚上，小北想给主页换一套深色风格，连改了两个小时 CSS，越改越不对劲：照片墙挤成一团，导航栏跑到了页面最底下。他想退回昨天那个好好的版本，却发现——根本没有"昨天那个版本"。文件夹里躺着的是：`index.html`、`index - 副本.html`、`主页最终版.html`、`主页最终版2.0.html`、`真的最终版.html`。挨个打开看，没有一个是他想要的样子。

这不是小北一个人的毛病。只要你开始写代码，就会遇到三件事：改坏了想回去、想试试新想法又怕弄坏现在的、换台电脑还想接着写。靠复制文件改名，这三件事一件都做不好。

这一章，我们给小北的网站装上 Git——一个专门管理代码历史的工具。学完后，他的网站每次重要修改都有存档，改坏了能退回，云端还有一份备份。**Git 不是编程语言，它是给你的代码买的一份保险。**

## 12.1 为什么需要版本管理：改坏了能回去

先说人话：**版本管理，就是给文件夹拍"存档照片"。**

玩过游戏的都懂存档：打大 Boss 前先存一个，打输了读档重来。写代码也一样——Git 让你随时给整个项目存一个档，以后不管改成什么样，都能回到任何一个存档点。

没有 Git 的时候，小北靠的是"复制文件改名"。这招有三个毛病：

1. **分不清谁是谁**。"最终版"和"真的最终版"，过一周你自己都不知道哪个更新。
2. **不知道改了什么**。两个版本差在哪全靠肉眼对，几百行根本对不出来。
3. **占地方又容易乱**。每个版本一整套文件，网站一大，文件夹就成了垃圾场。

Git 把这三件事都解决了：每次存档（后面会知道，这叫"提交"）都记下时间、作者和你写的说明；两个版本的差别能一行一行列给你看；而且它只记变化的部分，不占多少空间。

再多说一句：**Git 是全世界程序员都在用的工具**。以后实习、找工作、和别人合作写代码都绕不开它。拿自己的小网站练手最划算——项目小、改坏了不心疼，命令却和大厂工程师用的同一套。

这一章会用到终端。VS Code 自带终端（第 2 章见过）：打开网站文件夹后按 `` Ctrl + ` ``（Mac 相同，反引号键在数字 1 左边），下方就会弹出，它自动停在你打开的文件夹里。本章命令都在这里输入，输完按回车。

## 12.2 仓库与提交：init、add、commit 三件套

先把工具装好。Git 是免费软件：

- **Windows**：打开官网 `git-scm.com` 下载安装包，一路点"下一步"，选项全部保持默认。
- **Mac**：打开"终端"，输入 `git --version` 回车。没装过的话，系统会弹窗提示安装开发者工具，点"安装"等它装完就行。

装完后，在 VS Code 的终端里验证：

```bash
git --version
```

**这条命令做了什么**：确认 Git 装好了。看到类似 `git version 2.47.1` 就是成功；如果提示 "command not found"，说明没装好，重装一遍再来。

第一次用 Git，要先告诉它你是谁——每次存档都要"签名"：

```bash
git config --global user.name "小北"
git config --global user.email "xiaobei@example.com"
```

**这两条命令做了什么**：把你的名字和邮箱写进 Git 的全局配置（邮箱填常用的，后面注册 GitHub 用同一个最省事）。没有输出就是成功——**终端里"没报错"往往就是成功了**。这个配置只需做一次。

现在给小北的网站建一个"仓库"。仓库（repository）就是被 Git 管理起来的文件夹——普通文件夹加上一个隐藏的存档库。在 VS Code 里打开网站文件夹，在终端里输入：

```bash
git init
```

**这条命令做了什么**：把当前文件夹变成 Git 仓库。看到 `Initialized empty Git repository in ...` 就成功了。文件夹里会多出一个隐藏的 `.git` 文件夹，存档全在里面——**千万别删它，删了等于把保险柜砸了**。平时看不见它很正常。

接着看看仓库现在的状态：

```bash
git status
```

**这条命令做了什么**：报告仓库的当前情况，是你以后最常用的命令之一。你会看到 `Untracked files:` 下面用红字列着 `index.html` 等文件名，意思是"这些文件我还没开始管"。它什么时候都能运行、不会改动任何东西，养成习惯：**不知道现在什么情况时，先运行它**。

存档分两步。第一步，把想存档的文件放进"暂存区"：

```bash
git add .
```

**这条命令做了什么**：暂存区可以理解为拍照前的摆位区——先把这次要拍进存档的东西摆好。`.` 表示"当前文件夹里的全部改动"，也可以只摆一个：`git add index.html`。没有输出就是成功；再运行 `git status`，文件名变绿、挪到 `Changes to be committed:` 下面，就是摆好了。

第二步，正式存档，这个动作叫"提交"（commit）：

```bash
git commit -m "第一个版本：纯 HTML 个人主页"
```

**这条命令做了什么**：把暂存区里的内容拍成一张正式存档，`-m` 后面引号里的话是这张存档的说明，以后翻历史全靠它。看到类似下面的输出就是成功：

```bash
[main (root-commit) a1b2c3d] 第一个版本：纯 HTML 个人主页
 4 files changed, 523 insertions(+)
 create mode 100644 index.html
```

分支名你那边可能是 `main` 也可能是 `master`，都正常，12.4 推送前会统一。再运行 `git status`，看到 `nothing to commit, working tree clean`，就是全部存好了。

把这个节奏记牢，以后每次都是它：**改代码 → `git add .` → `git commit -m "说明"`**。提交信息要用一句话说清"这次改了什么"，比如"待办清单加上删除按钮"，不要写"改了一下""更新"这种自己三天后都看不懂的话。

## 12.3 查看历史与后悔药：log、diff 与回退

存了几个档之后，你会想翻翻账本：

```bash
git log --oneline
```

**这条命令做了什么**：一行一个存档，从新到旧列出所有提交。前面一串字母数字是存档的唯一编号（叫哈希值，记住前几位就够用），后面是你写的提交说明。不加 `--oneline` 的 `git log` 会显示完整信息（作者、时间等），信息太多，平时用简版就行。想退出列表界面，按 `q` 键。

改了几行代码、还没存档，想知道自己到底动了哪里：

```bash
git diff
```

**这条命令做了什么**：把"当前文件"和"上一个存档"逐行对比。带 `-` 的红行是删掉或改掉的旧内容，带 `+` 的绿行是新内容。**提交之前先 `git diff` 看一眼**是老手的好习惯，能拦住不少手滑，比如误删了一整段 CSS。

接下来是后悔药。分三种情况，从轻到重：

**情况一：改乱了，还没 add，想全部推倒重来。**

```bash
git restore index.html
```

**这条命令做了什么**：把 `index.html` 恢复成上一个存档里的样子，你刚才的改动全部消失。注意，**这是真消失、找不回来的**——restore 之前先想三秒，确定不要了再执行。

如果想一次恢复所有文件的改动，把文件名换成 `.`：

```bash
git restore .
```

**情况二：已经 add 进了暂存区，但还没 commit，想反悔。**

```bash
git restore --staged index.html
```

**这条命令做了什么**：只把文件从暂存区拿出来，文件内容一个字都不动。你可以继续改，或者再用情况一的命令彻底恢复。

**情况三：已经 commit 了，想回到前几天某个版本看看。**

先用 `git log --oneline` 找到那个版本的编号，然后：

```bash
git checkout a1b2c3d
```

**这条命令做了什么**：把整个文件夹切换到那个存档当时的样子，VS Code 里会直接看到旧版代码。终端会打印一大段 `detached HEAD` 提示，看着吓人，其实只是提醒你"你在参观旧版本，别在这里改东西"。参观完，输入下面这条回到最新版：

```bash
git switch main
```

（你的分支名若是 `master`，就写 `git switch master`。）**这条命令做了什么**：把你带回主线的最新状态。记住一个原则：**旧版本只看不改**。

## 12.4 GitHub：把代码放到云端

到现在为止，存档都只在你自己电脑里——电脑丢了、硬盘坏了，保险柜跟着一起没。这一节把仓库同步到 GitHub：全球最大的代码托管网站，可以理解为"代码的网盘"，免费账号就够学生用。

第一步，打开 `github.com` 注册账号（邮箱就用 12.2 里配的那个），登录后点右上角 `+` 号，选 `New repository`。要填的只有两项：**Repository name** 填 `xiaobei-site`（英文、短横线连接）；**Public / Private** 选 Public，练手项目公开没关系，展示给老师和面试官看反而方便。下面的初始化选项（Add a README file 等）**全部不要勾**——本地已经有仓库了，勾了反而容易对不上。

点 `Create repository` 后，GitHub 会给出几行现成命令。在 VS Code 终端里依次运行这三条（用户名换成你自己的）：

```bash
git remote add origin https://github.com/你的用户名/xiaobei-site.git
```

**这条命令做了什么**：给本地仓库登记云端地址，`origin` 是给这个地址起的固定外号，以后推送就喊它。没有输出就是成功。

```bash
git branch -M main
```

**这条命令做了什么**：把本地主线分支改名为 `main`，和 GitHub 的习惯一致。没输出就是成功。

```bash
git push -u origin main
```

**这条命令做了什么**：把本地所有存档推（push）到云端。第一次推送会弹出浏览器让你登录 GitHub 授权，照提示走完就行；看到 `branch 'main' set up to track 'origin/main'` 就是推上去了。`-u` 只在第一次需要，意思是"记住本地 main 和云端 main 的对应关系"，以后推送只需两个字：

```bash
git push
```

刷新 GitHub 仓库页面：文件都在，提交说明也在——**你的代码在云端有家了**。以后节奏变成三连：`git add .` → `git commit -m "说明"` → `git push`，云端本地永远同步。

最后一个概念：克隆（clone）。换台电脑、或想把同学的公开项目拿下来学习时用它：

```bash
git clone https://github.com/某人的用户名/仓库名.git
```

**这条命令做了什么**：把云端仓库连文件带全部历史整个下载下来，并自动配好 origin。下载完 `cd` 进去就能接着写。另外，把云端的新存档拉回本地用 `git pull`——push 往上推，pull 往下拉，方向别记反。

## 12.5 分支：在平行宇宙里试新想法

![图：Git 分支与合并示意](../images/fig-ch12-git-branch.svg)

到目前为止，所有存档排成一条直线，这条线叫"分支"（branch），你一直用的这条主线就叫 `main`。但小北有个新烦恼：他想试一个大改版——把主页配色全换掉、布局重排。可万一新版不好看，现在这个好好的版本不能陪葬。

分支就是为这个场景生的：**从当前版本分叉出一条平行线，在新线上怎么折腾都不影响主线；做满意了，再把成果合并回来；不满意，删掉这条线，主线毫发无损。**

看看自己现在有哪些分支：

```bash
git branch
```

**这条命令做了什么**：列出全部分支，带 `*` 号的是你当前所在的那条，现在应该只有一条 `main`。

给小北的大改版开一条新分支，并立刻切换过去：

```bash
git switch -c new-design
```

**这条命令做了什么**：`-c` 是 create——新建叫 `new-design` 的分支并把你送进去。看到 `Switched to a new branch 'new-design'` 就是成功。现在随便改，改完照常存档：

```bash
git add .
git commit -m "大改版第一稿：深色配色"
```

这个存档只在 `new-design` 分支上，主线 `main` 完全不知道。想回主线看看原来的样子：

```bash
git switch main
```

VS Code 里的文件会"唰"地变回改版前——不是文件被删了，是你换了一个平行宇宙。对比之后觉得新版更好，就把成果合并回主线：先站在主线上，再执行合并：

```bash
git merge new-design
```

**这条命令做了什么**：把 `new-design` 的存档合并进当前分支（main）。主线在改版期间没被动过的话，你会看到 `Fast-forward`，意思是主线直接快进到新版位置。用完的分支可以删掉：

```bash
git branch -d new-design
```

如果改版试了三天发现还不如原版呢？切回 `main`，**什么都不合并**，直接删掉分支，新版就当没发生过。**分支的核心价值就一句话：让"试错"变得几乎零成本**。以后试新配色、试新功能、跟着后面章节重构代码，都先开条分支再动手。

偶尔合并会遇到"冲突"：同一处两条线都改了，Git 不敢替你做主，会在文件里标出分歧让你选。这是进阶话题，本章不展开——只要知道：遇到冲突不要慌，它不会弄坏存档，按标记二选一即可。

## 12.6 贯穿作品：小北的网站有了保险箱

来把这一章完整走一遍，给小北的网站正式上保险。

小北把前面十一章的全部成果——`index.html`（主页）、`style.css`（排版美化）、`script.js`（待办清单与天气小应用）——一次性纳管：

```bash
git init
git add .
git commit -m "第一个版本：主页、待办清单与天气小应用"
git remote add origin https://github.com/xiaobei/xiaobei-site.git
git branch -M main
git push -u origin main
```

（用户名、仓库名按你自己注册的填。）六条命令跑完，小北在 GitHub 页面第一次看到自己的代码整整齐齐躺在云端，还点开 `index.html` 的 History 看到了第一个存档——从今天起，他的网站有了完整的"成长档案"。

从这一章开始，小北（还有你）的日常开发节奏固定为这套动作：

1. 写一段代码，浏览器里确认效果对了；
2. `git add .` 把改动摆上暂存区；
3. `git commit -m "这次改了什么"` 拍一个存档；
4. 收工前 `git push`，把今天的存档同步到云端。

**存档的频率比什么都重要**：一个功能做完存一次，下课前存一次，别攒一周才提交。存档越密，出事时损失越小——这正是重构 React 之前先学 Git 的原因：下一章要动大手术，而现在，手术台下已经铺好了安全网。

## 本章要点

- 版本管理就是给代码存档：改坏了能回到任何一个存档点，靠复制文件改名做不到这一点。
- Git 第一次使用前要安装并配置用户名、邮箱；用 `git --version` 和 `git status` 随时确认状态。
- 存档两步走：`git add` 把改动放进暂存区，`git commit -m "说明"` 正式提交；说明要写清这次改了什么。
- `git log --oneline` 看历史，`git diff` 看还没存档的改动，提交前先看 diff 是好习惯。
- 后悔药分三档：`git restore 文件` 撤销没提交的改动，`git restore --staged 文件` 撤出暂存区，`git checkout 编号` 只参观旧版本、不在旧版本上改东西。
- GitHub 是代码的云端仓库：`git push` 把存档推上去，`git clone` 把仓库连历史一起下载下来，`git pull` 把云端的新存档拉回来。
- 分支是平行线：大改版先开分支试验，满意了 `git merge` 合并回来，不满意删掉分支，主线不受影响。

## 动手 Kata

**练习 1：给你的网站建仓库。** 在 VS Code 打开网站文件夹和终端，依次完成：配置用户名邮箱（第一次才需要）、`git init`、`git status`（确认文件名是红色的 Untracked）、`git add .`、`git commit -m "第一个版本"`。做完应该看到：再运行 `git status` 显示 `working tree clean`。

**练习 2：试一次后悔药。** 改 `index.html` 里一处文字，运行 `git diff` 确认能看到那行绿色的 `+`，然后运行 `git restore index.html`。做完应该看到：刷新主页，文字变回原样，`git diff` 不再有任何输出。

**练习 3：把代码推上 GitHub。** 按 12.4 注册、建空仓库（不勾初始化选项），运行三条命令完成第一次推送。做完应该看到：刷新仓库页面，全部文件都在，点提交记录能看到第一次提交。

**练习 4：开分支试一次大改。** `git switch -c try-color` 开新分支，把主页背景改成一个你绝不会用的颜色，提交；`git switch main` 确认颜色恢复原样；再 `git merge try-color` 合并回来，刷新确认变成尝试版。最后想一想：如果不喜欢这个结果，合并前应该怎么做？做完应该看到：`git branch` 列出两条分支，带 `*` 的是你所在的那条。

**练习 5：异地取档体验。** 新建一个空文件夹，在里面运行 `git clone https://github.com/你的用户名/xiaobei-site.git`。做完应该看到：完整的网站文件出现在文件夹里，双击 `index.html` 能打开——将来换电脑继续写代码就靠它。

## 翻车现场

**"我就改一点点，不用提交"——小北在 main 上直接试验，改崩了。**

学完 Git 的第二周，小北看到一个很火的配色方案，手痒想试。他想着"就动几个颜色值，五分钟的事"，没开分支、也没先提交，直接在主线开改。改到一半发现新配色跟照片墙边框不搭，顺手又调布局，调布局时删了 Flex 的一行，照片墙塌了；凭记忆往回改了四十分钟，页面比最开始还乱。想读档才发现：**上一个存档还是一周前的，昨天的样式优化根本没提交过**。退回一周前要丢一周成果，不退眼前是一团乱麻。最后他花了两个小时把代码一行一行重写回来。

这次翻车错在两处。第一，**动手大改之前没先存档**——存档点之间隔得越久，出事时要丢的东西越多，"改一点点"正是翻车的经典开场白。第二，**试验性改动直接在主线上进行**——分支就是为这种时刻准备的，开分支只要一条命令，试坏了删掉就行。

记住这条规矩：**任何"试试看"的改动，先 `git commit` 保住当前的好版本，再 `git switch -c` 开个新分支去试。** 存档和分支加起来不到十秒钟，能省下两小时的重写。
